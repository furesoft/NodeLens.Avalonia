# Interactive language documentation

**Status: planned, not built.** This document is the design a session implements; nothing here exists yet beyond the
inputs it reads.

## What it is for

A language that lives in a folder is readable by whoever wrote it and by nobody else. The registry knows everything a
reader needs - the concepts, their slots, what inherits from what, which notation draws them, what the constraints say -
but it is only visible through the editor, one document at a time. The documentation generator turns a
`LanguageProject` into a folder of static HTML a team can open in a browser, link into a wiki, or ship beside a
package.

**Static files with a script, not a server.** The output is a folder that works from `file://`, from a web server, and
inside a zip. That rules out anything that needs a process: no search endpoint, no live rendering. What makes it
*interactive* is therefore client-side and small - a search box that filters the concept index, collapsible sections,
anchors that link into a page, and a hover that shows a concept's description where its key is used.

## What it contains

| Page | Content |
| --- | --- |
| `index.html` | the language's name and description, a search box over concepts, and the concept list grouped by inheritance root |
| `concepts/<key>.html` | one page per concept: key, name slot, description, super concepts and interfaces with links, every slot as a row (kind, key, type or target, cardinality, default), and the notation that draws it in the notation language's own spelling |
| `aspects.html` | what lowering produced from each aspect folder: concepts, notations, type rules, constraints, scope rules, intentions, generators, importers - the same facts the module settings dialog shows, in a page a reader can link to |
| `examples.html` | one example per concept the language can root, rendered by the projection's headless snapshot renderer, so the page shows what the concept *looks like* rather than describing it |
| `assets/docs.css`, `assets/docs.js` | the one stylesheet and the one script, both deterministic, both small enough to read |

Two rules come from the repository's own invariants:

- **The output is derived and byte-stable.** Same `LanguageProject` in, same bytes out - no timestamps, no
  machine-specific paths, no hash-ordered lists. Concept pages are ordered by key, slots by declaration order, because
  those are the orders the registry already promises.
- **The pages never claim more than the model says.** A concept with no notation says so; a language with no
  constraints lists none. An empty aspect is a fact, not an omission - the same rule the module settings dialog follows.

## Where it lives

`src/Projectional.LanguageDocs/` - a new package, because it is a product a host can reference and call
(`LanguageDocumentation.Write(language, directory)`), and because every project under `src/` is a package
([ADR 0022](../adr/0022-every-project-is-a-package.md)). Adding it means the CI `pack` job's package count moves from
32 to 33 in the same commit.

It references `Projectional.Languages` (the lowered project) and `Projectional.Projection` (the snapshot renderer for
the example pages) - both downward arrows, so nothing new points up. It must **not** reference Avalonia: documentation
is generated by a build, a test, or a CLI, never by a window.

The shell gets one command for it - **File ▸ Export documentation…** - written like `LanguageExportWriter`, which is
the pattern this repository already has for "a menu entry that writes a folder".

## What has to be decided first

These are the questions the implementation answers, not this document:

1. **Images or layout in HTML?** The snapshot renderer produces a layout, not a bitmap. Drawing the notation as inline
   SVG keeps the output text (diffable, searchable, no raster step); writing a PNG per example needs a rendering
   backend and makes the output binary. Recommendation: SVG, because the whole product's premise is that the drawing is
   derived from the model.
2. **Does the search index live in the page or in the script?** A JSON index inlined into `index.html` keeps the folder
   free of fetches (`file://` refuses them); a separate `assets/index.json` keeps the page small. Recommendation:
   inline, capped - a language with thousands of concepts is a language whose index needs its own file, and that is a
   decision to take when one exists.
3. **How much of the notation is shown?** Rendering every concept with a sample node means synthesising children, which
   can be impossible (a child slot with a minimum). Recommendation: draw the notation with placeholders, the same way
   the editor draws an empty slot, and say in the page that it is the shape rather than a document.
4. **Is an example a model or a string?** A language that ships `tests/` already holds models that draw. Reading them
   gives real pictures and needs no synthesis - but it makes the documentation depend on the tests' shape.
   Recommendation: render the tests' models when a `tests/` folder exists, and fall back to placeholders.

## How it is proven

- A fixture language (the repository's `declared-pipeline`) is generated into a temporary directory, and the test
  asserts: every concept has a page, every link in every page resolves to a file that exists, a slot appears with its
  kind and its target, a concept with no notation says so, and two runs produce identical bytes.
- One test reads the generated HTML as text and asserts that no `<script>` of ours runs before the search index is
  defined - the failure mode of a static page with a script is a page whose search silently does nothing.
- A picture is not part of it: the output is HTML, and the repository's screenshot tool is for the editor and the shell.
